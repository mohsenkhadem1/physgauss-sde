SCENE / CONTACT INPUT AUDIT
SoftVT HDF exposes initial_state/rigid_object/<name>/root_pose and root_velocity,
and states/rigid_object/<name>/root_pose over the entire future sequence.
Only INITIAL state or observed-prefix environment geometry may enter prediction
unless an entity is explicitly an externally prescribed control. Future moving
obstacle states are labels, not permitted inputs to a coupled-object predictor.
The soft_pastry*_tactile_proxy is a target-linked proxy. EXCLUDE it entirely:
using its future pose leaks future target motion even though the path says rigid.
Do not use target-language goal position as observed landing/contact geometry.
Local scene_params.json provides placement data but not full collision surfaces.
No relevant plate/basket USD/OBJ mesh was found under the local runs file tree
by filename search. Poses alone do not establish real collision geometry. If
approximating with planes/bowls, declare primitive geometry and choose dimensions
from public asset metadata/mesh or development observation, never future targets.
If v12 receives scene geometry absent from v11/PhysTwin, label the extra input
and compare a geometry-matched contact/rigid baseline. Report a same-input
ablation too, so gain from geometry is separated from new material inference.
Rigid/deformable labels can be known in a simulation experiment; do not pretend
they were inferred. More objects plus static contact does not demonstrate coupled
dynamics unless the second movable object is predicted and independently scored.

PREFIX CONTACT-STATE CLASSIFIER / FALLBACK AUDIT
A closed gripper command does not establish that the object remains attached.
It is scientifically reasonable to infer attached, detached-moving, or resting
from observed object and tool motion, provided the following constraints hold:
1. Thresholds, window lengths, confidence scores, and guard tolerances must be
   selected on the declared development20 + single_lift_sloth only. Never tune
   using old benchmark suffix errors even though those errors are known.
2. A classifier applied at train_end may inspect only frames strictly before
   train_end. It cannot mark future transitions using actual future object motion.
   If its state persists or changes predictively, state that assumption explicitly.
3. Compare OBJECT-TOOL RELATIVE motion and world object motion. Slow world motion
   alone cannot distinguish a static held object from a resting one. A detached
   object need not be stationary, and a grip can slip while partially constrained.
4. Use observed positions/visibility, not force/tactile channels, success flags,
   future proxy/scene state or future target data. An uncertain state should be
   represented/handled explicitly, not assigned from target behavior.
5. Prefix temporal crossvalidation is a fair per-case model-selection rule ONLY
   when every candidate is fit on the reduced earlier prefix and rolled out over
   the hidden later prefix. Reusing parameters fit to the entire prefix to score
   its last segment leaks validation observations and favors high-capacity fits.
   Geometry calibration, contact classifier and attachment offset must also be
   recomputed using only the earlier prefix. Caching the full-prefix adapter and
   merely shortening observed[] does NOT suffice: grasp calibration can leak.
6. Freeze the validation fraction (e.g. final quarter of observed prefix), minimum
   frame count, allowed candidate set and tie/default rule on development. Then
   choose using validation only; refit the chosen candidate on full observed
   prefix. A v11 fallback must itself be evaluated under the same reduced-prefix
   fit budget and geometry inputs. Report selected model and validation scores
   per sequence, plus standalone v12 results alongside guarded results.
7. A state/parameter estimated from the final available observation is legitimate
   forecasting initialization, but disclose the distinction from v11's open-loop
   rollout-from-t0. Include a v11 or rigid baseline with the same observed-prefix
   reset to separate assimilation benefit from contact modeling benefit.
8. If validation contains no release/contact switch, it cannot validate that
   candidate's release dynamics. Do not extrapolate confidence from held-only
   validation; report phase coverage and preserve all full-suffix results.
