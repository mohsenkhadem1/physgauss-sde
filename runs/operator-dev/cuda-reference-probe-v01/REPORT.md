# Float64 CUDA reference probe, 2026-10-21

The separate CUDA wrapper passed seven tiny mechanics controls and one previously qualified TRAIN t0001/480 Hz replay, but was slower than the captured CPU execution. Keep the CPU solver for current production work. This is a successful narrow parity test and negative initial performance result, not broad GPU qualification.

The wrapper preserves the original physical method/helper code objects in a private namespace, changing only tensor allocation/device placement. CPU assembly is copied to CUDA float64, all masses/inertias/constraints/energies, integration, residual tolerances, positive-J rejection, line search and full balance telemetry are unchanged. Shared module bindings and physical sources were verified unchanged. No TF32, mixed precision, residual relaxation, training, reserved inputs or new force envelope was used. The physical core remains SHA256 `da0db7018b4913020bb228c2fc4df3c240e7dd872f17db4868de147eaaf78fa2`; wrapper SHA256 is `3885af3bbe12246046e6caa38470988b5dac3bfd7c85441b19b81a2a12ab98f2`.

Four CPU unit tests passed: method/helper identity and shared binding preservation, bitwise CPU wrapper parity, rejection of foreign-device allocation, and copy isolation. Seven tiny GPU controls covered zero rest with all four fixture types, analytic uniform acceleration, finite rigid rotation with held force/full inertia, and an accelerating prescribed boundary. Maximum CPU/GPU q and v differences were 2.78e-17 m and 4.16e-17 m/s. Tiny-control timings include assembly, transfers and comparisons and are not a speed benchmark.

The one full replay used exactly the captured 1440 commands over 3 s, preserving 31 actual 10 Hz states. Maximum absolute errors: q 5.55e-16 m, v 1.33e-14 m/s, handle centers 8.33e-17 m, rotation entries 1.54e-14. Per-step minimum-J differences were at most 5.88e-15. Every original residual gate passed; force commands and accumulated impulses matched exactly. Maximum reported elastic/kinetic/total energy discrepancies were 3.98e-19 J or less. Energy discrepancy was reported, not an independently predeclared acceptance gate. Full-case auxiliary point velocities were not saved by the CPU reference, so pointwise parity for those is established only in tiny controls.

CUDA step time including unchanged balance telemetry was 305.15 s versus captured CPU 129.02 s (2.365 times slower). End-to-end CUDA was 309.73 s versus captured CPU 133.25 s. CPU assembly/transfer took another 0.768 s; sampled state D2H 0.00788 s, JSON I/O 0.482 s and OS telemetry 3.941 s. The CPU run also included per-step geometry eigvalsh telemetry omitted in this probe, and contention differed: these are initial-path timings, not a matched benchmark speedup. CUDA peak allocated/reserved memory was 123,521,024/142,606,336 bytes.

CPU tiny-control profiling identifies repeated autograd backward as the dominant path; the captured full case averaged 2.58 nonlinear updates and at least 6.16 evaluations per step. A passive sample showed 13% GPU utilization and roughly one host core occupied, consistent with host synchronization/launch overhead but not a kernel-level attribution. The wrapper deliberately retains scalar decisions, full balance telemetry and original repeated evaluations. A future separately validated implementation could investigate accepted-evaluation caching, independent-hypothesis batching with individual line-search gates, or fused float64 kernels. None was attempted here.
