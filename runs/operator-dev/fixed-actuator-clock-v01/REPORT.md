# Fixed known-actuator clock component

New source: `experiments/campaign_fixed_actuator_clock.py`, SHA256 `1b1361696a3822e608687620b39363ef6667060ed4c313932daac3151e000c5f`. Forty-four offline tests passed in 0.75 s. No physics, GPU work, response trajectory, recipe or material/boundary input was used. Twelve existing published runner/auditor/compiler/context/core/driver/config files were checked byte-identical to HEAD; none was edited.

`FixedActuatorClock` accepts only an explicit integer actuator Hz, exact endpoint times, requested output times, held world handle forces, pure torques, nodal forces, uniform body acceleration and mandatory `known_actuator_command` role. Endpoint times must be exactly `arange(T+1)/actuator_hz` from zero in float64; outputs must be an increasing subset of those endpoints. Ambiguous clocks are rejected, never snapped or interpolated. Float32 command values are promoted exactly; lossy wider-float/integer conversion is rejected. Input arrays are copied to immutable bytes-backed float64 storage.

`from_force_program` accepts the exact existing typed ForceProgram with the known-command role. It reads only role and command arrays, and does not copy source metadata that could contain oracle labels. Candidate-force roles and untyped substitutes are rejected. This preserves declared known commands; it cannot establish that the caller was justified in declaring a command known.

`repeat_for_integration(clock, integration_hz=...)` accepts only a private Hz that is an integer multiple of the fixed actuator Hz. It repeats every held command over its integer substeps, preserving exact public endpoints and explicit output alignment. Coarser, nonaligned, float and boolean rates fail. No force waveform is evaluated, and no torque/acceleration is converted into a different load representation. Float64 exact-integer clock/index limits are checked; ordinary finer integer multiples have no enumerated rate menu. Available memory still limits materializing large repeated schedules.

Public feature arrays and their manifest contain only the fixed known command clock/values/role. They are byte-identical across private rates; private Hz, repeat factor, command-parent indices and output-step indices remain in the separately returned private execution schedule. Relabelled dummy latent contexts cannot enter the explicit API. The caller must freeze a common actuator clock independently of material/boundary labels; this component cannot police an external caller's clock-selection policy.

Synthetic randomized tests use public rates 5/20/960 Hz and integer refinement factors 1/2/3/7/16. They check exact role/held-value equality, each side of command jumps, endpoint/output alignment, public-manifest invariance, immutable copies, independent long-double rectangular impulse and temporal first-moment checks, zero-resultant couples, explicit pure torques and uniform acceleration with zero handles/nodal loads. The separate 960 Hz synthetic probe reports at most 5.04e-17 absolute difference between original and subdivided command integrals, with invariant public manifest across factors. Force/torque impulses and integrated acceleration are separately labelled in their proper units; these are compiled-command diagnostics, not measured solver impulses or work.

One initial test assertion was too broad: it rejected the substring `boundary` inside the legitimate `command_boundary_times_s` field. The assertion was corrected to reject latent `boundary_type`; the component's behavior was not changed for that assertion. All 44 final tests pass.

No continuous boundary/support law is inferred or implemented. Finer support commands require a separately specified and validated extension. Compiled times are requested grids; a future integrator must separately measure and record accumulated state clocks. No dataset, physical convergence, inference or policy is qualified.

This does not retrofit the current 119-cell engineering campaign. That campaign evaluates its authored waveform on each solver's midpoint grid; repeating a newly fixed command grid defines a different forcing discretization. A future common-clock dataset/forward model needs its own prospective declaration and numerical checks. For example, a fixed 960 Hz actuator clock requires every private solver rate to be at least 960 Hz and aligned; this helper rejects a 120/240/480 Hz solver instead of changing the physical command. All current frozen campaign evidence and failures remain unchanged.
